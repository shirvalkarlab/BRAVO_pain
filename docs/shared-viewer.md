# Shared lab viewer

The shared lab account is for viewing existing participant data and reports. It
uses normal browser sign-in, with a separate session for each browser. Signing
out of one browser does not sign out the others. The account's institute and
permissions are assigned by the administrator; changing browser display filters
does not grant access to another participant.

The server exposes `ReadOnly` in the authenticated profile. An administrator
provisions this account with `configuration.SharedReadOnly = true` and a `Viewer`
institute membership. Ordinary signup cannot set this flag or grant lab access.
No schema migration is needed. Keep the generated password in the private
credential handoff, never in this repository, an issue, or a support message.
Rotate it through the administrator if access needs to be withdrawn.

## What viewers can do

View authorized participant information, native BRAVO reports, Prasad's analysis
modules, and all seven Aditya tabs. Display filters and chart selections remain
available where they only affect the requested view. Refresh view reloads the
latest available saved data; upstream freshness still depends on the normal
administrator-managed imports. Canonical analytical readers can populate derived
caches and perform their existing read-only provider queries. Read-only does not
mean that sessions, cache files, or access logs never change.

Viewers cannot upload, import or delete data; run synchronization; edit annotations,
participant/device details, shared processing settings or saved chosen bands;
start background preprocessing; connect provider accounts; create studies or
invitations; obtain API/desktop credentials; export full participant backups or
write Google Sheets. Full backups are excluded because they can contain provider
credentials. Existing burst results are viewable, but missing preprocessing must
be generated by an individual authorized account.

The policy fails closed for unreviewed endpoints, operations and parameters,
including write operations hidden inside query APIs. API-key, desktop-token and
Basic authentication are unavailable for the shared viewer. Backend checks remain
authoritative even if someone changes the browser UI. Normal individual accounts
retain their existing permissions.

## Verification and operation

Synthetic tests exercise real Django login, CSRF, independent sessions, participant
isolation, denial of mutations and alternate authentication, secret redaction, and
non-creation of missing wearable devices. CI also verifies every API route uses a
guarded authentication class and requires at least 95% branch coverage in the
viewer policy and authentication adapters.

Twenty independent sessions are an acceptance target, not a claim that twenty
uncached heavy analyses will finish instantly. Deployment acceptance must record
the exact version, representative authenticated report reads, a bounded concurrent
read check, and unchanged owner access/services/timers before giving out the login.
