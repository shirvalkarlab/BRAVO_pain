# Preserve client identity through the local proxy

The localhost appliance receives requests through Tailscale, Nginx and Uvicorn.
Appending the Docker bridge address to Tailscale's forwarded origin made Uvicorn
attribute every public visitor to that bridge. The inherited anonymous-page
limiter could then create a persistent gateway-wide ban, while health endpoints
continued to pass and the login page returned the legacy404 template with HTTP200.
The appliance readiness command now requires client-bundle markers as well as the
page title, so that error template cannot be mistaken for the running application.

Nginx now preserves the verified upstream origin, falling back to the connection
address for direct local requests without that header. It strips the misspelled
`X-Forward-For` header, and the homepage uses Uvicorn's resolved `REMOTE_ADDR`.
Authentication, existing blacklist enforcement, the anonymous-page limiter and
Uvicorn's loopback-only proxy trust remain unchanged.

This configuration relies on the listener remaining bound to localhost behind
Tailscale, with host processes and the private backend network trusted. It is
not a general configuration for a directly exposed Nginx listener or another
proxy that accepts client-supplied forwarding headers. The installed Tailscale
1.102.3 behavior was checked against its
[official forwarding implementation](https://github.com/tailscale/tailscale/blob/v1.102.3/ipn/ipnlocal/serve.go#L996-L1003),
which sets the forwarded origin from the connection context.

Portable component tests exercise the actual Nginx configuration and Uvicorn on
isolated container loopback ports, including IPv4/IPv6 origins, absent headers,
all four proxy routes, spoofed alternate headers and explicit bans. They publish
no host ports and use no deployment data. Final acceptance also requires normal
public Chrome login, viewer reads/logout, exact published-SHA CI, image identity
and a live forwarding check through the existing public route.

For recovery from an already-created false-positive proxy ban, first verify the
actual gateway, exact automatic record, creation time and reason. Privately back
up that record before a targeted administrative removal. Never clear all bans or
ignore manual bans by reason; do not restore older participant data. The retained
limiter may still ban an individual actual origin after repeated page requests;
this change specifically removes shared-proxy misattribution.
