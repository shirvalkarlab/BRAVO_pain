**How this review was done.** I read every report end to end, then went looking for what would
break if the plans were actually carried out: a real clinic day, a real deploy, a real failed
container. Where a claim about the device could be checked outside this project's own files, I
searched the web and say so; where I could not confirm something either way, I say that too,
plainly, rather than guessing.

| **CRITICAL** | Report 02, Part 3 preparation step 2 ("Single Threshold Inverse" as a safe, sensing-only way to log a band at home) | The report treats this device mode as one that logs a band without ever changing the current delivered, citing this project's own `DEVICE_percept_rc.md`. ## The protocol as it could actually run

A corrected order for report 02, given the findings above. Nothing here is a green light — every step
still needs the PI's explicit go-ahead and, for the pieces marked below, a research-ethics check first.

1. **Before scheduling anything:** confirm two things that block everything else. First, that
   RCS08's IRB protocol already covers a deliberate stimulation-off block and a blinded multi-day
   home sequence (CRITICAL finding above) — if not, this is a protocol-amendment conversation, not a
   scheduling one. Second, run the one live comparison report 06 already specifies for the possibly
   stale Closed-Loop numbers, since the visit's own design leans on the same machinery.
2. **Confirm the device facts the protocol assumes**, in writing, from Medtronic clinical support or
   the treating clinician's manual, not by inference from either this project's notes or a web
   search: (a) whether "Single Threshold Inverse" truly never changes the delivered current on this
   firmware, or whether it is an active, reversed-direction control law; (b) whether changing only
   the pulse rate causes any momentary drop in delivered current; (c) whether the patient's own
   take-home controller can trigger anything beyond the passive 10-minute chronic log.
3. **Run the rate swap (Part 2) first, as the synthesis already recommends**, but state its "no
   interruption" claim as unconfirmed until step 2(b) answers it, and budget clinician/technician
   time (roughly 1-2 hours of continuous hands-on tablet work), not only patient time.
4. **Run the tightly-timed zero-current block (Part 1) only after a fresh, explicit safety and
   research-ethics review**, and pair the recommendation to run it with the honest expectation,
   stated in the same breath: even a clean result will still be "a lead," not a settled finding,
   because the record cannot reach the number of separate days a real answer would need.
5. **Hold Part 3 (the take-home hold-and-return) until step 2(a) is answered.** If "Single Threshold
   Inverse" turns out to be an active control mode, Part 3 as written has no safe way to log a band
   at home without also changing therapy, and needs a different mechanism — for instance, leaving the
   chronic log exactly where it is today and accepting a less specific band, or skipping the
   continuous log and relying on the scheduled ratings alone. Also drop the word "blinded" for the
   amplitude changes until it is established the patient cannot feel the difference between the
   planned steps.
6. **Feed report 03's larger question (should time enter any model) from whatever step 5 actually
   produces**, not before — report 03 already says as much, but the synthesis should say so too,
   rather than listing it as blocked on "nothing new."
7. **On the build side, do the correctness check (item 3 above) and the host-only speed items first**
   if the container or bridge is not confirmed available for the session doing the work, since
   Biomarkers-module changes (the p-value fix, the band detector, the grid-median speed-up) cannot be
   tested or proven at all without it.
